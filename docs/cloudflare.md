# استقرار سه سایت روی Cloudflare Pages

این مسیر برای میزبانی Cloudflare انتخاب شده است. سایت شخصی در `/`، خروجی عمومی intmed در `/intmed/` و AUS در `/aus/` قرار می‌گیرند. مخزن‌ها ادغام یا ویرایش نمی‌شوند؛ فقط فایل‌های عمومی آن‌ها در زمان build کنار هم چیده می‌شوند. خروجی، فایل استاتیک واقعی است و برای بازکردن صفحه‌ها به GitHub در مرورگر کاربر وصل نمی‌شود.

## تنظیمات دقیق Pages

در **Workers & Pages → Create application → Pages → Connect to Git**، مخزن `4mirgr/gerami-website` را انتخاب کنید. یک پروژهٔ Pages جدید بسازید؛ Worker موجود `intmed-api-proxy` را با سایت جایگزین نکنید.

| تنظیم | مقدار |
|---|---|
| Production branch | `main` |
| Framework preset | `None` |
| Build command | `python3 -m pip install -r requirements-cloudflare.txt && python3 scripts/build_cloudflare.py` |
| Build output directory | `_site` |
| Root directory | خالی؛ ریشهٔ مخزن |

Python 3، Node.js و Git در محیط build باید در دسترس باشند؛ برای هماهنگی با CI خود intmed، `PYTHON_VERSION=3.12` و `NODE_VERSION=22` پیشنهاد می‌شود. تنها وابستگی اضافهٔ build، نسخهٔ قفل‌شدهٔ jsonschema برای اعتبارسنج رسمی محتوای intmed است؛ نصب npm یا Nginx لازم نیست. این build هیچ دستور deploy ندارد؛ انتشار توسط خود پروژهٔ Pages انجام می‌شود. اگر Git integration از قبل فعال است، push به شاخهٔ تولید می‌تواند انتشار Pages را آغاز کند.

Build، نسخه‌های دقیق ثبت‌شده در `deploy/projects.json` را دریافت می‌کند. موفقیت دریافت مخزن با اعتبارنامهٔ محیط توسعه، تضمین نمی‌کند Cloudflare هم به مخزن خصوصی دسترسی دارد؛ اگر یکی از دو مخزن خصوصی است، دسترسی امن build به همان مخزن باید از طریق تنظیمات سرویس فراهم شود، نه قرار دادن توکن در URL، کد یا چت.

بعد از اولین استقرار، نشانی `*.pages.dev` را برای نمایش صفحات و فایل‌ها بررسی کنید. دکمه‌ها در خروجی ترکیبی نسبی‌اند؛ بنابراین در پیش‌نمایش نیز به همان hostname و `/intmed/` و `/aus/` می‌روند. CORS فعلی API فقط دامنهٔ اصلی و www را می‌پذیرد؛ پیش‌نمایش Pages برای ورود واقعی به حساب تولید آماده محسوب نمی‌شود. برای حل این موضوع محدودیت Origin را عمومی نکنید.

## اتصال دامنه، بعد از بررسی staging

1. مشخص کنید اتصال فعلی دامنه به GitHub Pages یا سرویس دیگر کجاست؛ دریافت دامنه از nic.ir و استفاده از DNS Cloudflare به‌تنهایی به‌معنای میزبانی روی Pages نیست.
2. از رکوردهای فعلی و تنظیمات دامنه نسخهٔ قابل بازگشت نگه دارید. پس از بررسی staging، در پروژهٔ Pages از **Custom domains**، دامنهٔ `drgerami-md.ir` را اضافه و اتصال قبلی را در زمان انتقال تغییر دهید. رکوردهای ایمیل و API را تغییر ندهید.
3. Worker و دامنهٔ موجود `api.drgerami-md.ir` را نگه دارید. مسیر اختیاریِ موجود `/api/*` هم نباید به fallback صفحهٔ اصلی سایت تبدیل شود. منبع Worker در مخزن intmed تحت `backend/cloudflare/` است و این build آن را تغییر یا دوباره منتشر نمی‌کند.
4. در تنظیمات Supabase Auth، مقصد مجاز `https://drgerami-md.ir/intmed/` را برای recovery/invite در نظر بگیرید؛ تا پایان انتقال، لینک‌های قدیمی صادرشده را نیز بررسی کنید. مدیریت این تنظیمات به دسترسی مالک سرویس نیاز دارد.
5. صفحات اصلی، محتوای lazy-loaded، ورود/خروج، بازیابی حساب، ذخیره و همگام‌سازی، نصب PWA و نسخهٔ قبلاً نصب‌شده را روی دامنهٔ واقعی و دستگاه‌های موردنیاز بررسی کنید. آزمون محلی، ورود و ذخیرهٔ حساب واقعی یا سلامت API تولید را ثابت نمی‌کند.

در این گفتگو تغییر DNS، اتصال دامنه، تنظیم Supabase یا انتشار Cloudflare انجام نشده است.

## داده‌ها و وابستگی‌ها

- AUS بدون backend اجرا می‌شود و داده‌های اولیه را با آدرس نسبی از `data/` می‌خواند. وظایف و تنظیمات کاربر در localStorage همان مرورگر هستند؛ انتقال از hostname دیگری آن‌ها را خودکار به این hostname منتقل نمی‌کند. از خروجی JSON خود برنامه استفاده کنید.
- intmed به Supabase وابسته است و پیکربندی عمومی موجود آن از `api.drgerami-md.ir` استفاده می‌کند. anon/publishable key عمومیِ موجود برای مرورگر باقی می‌ماند؛ کلید خصوصی یا service-role وارد خروجی نمی‌شود. شناسه‌ها و داده‌های کاربران دست‌کاری نمی‌شوند.
- چون مسیر جدید intmed روی همان origin دامنهٔ اصلی است، کلیدهای فعلی مرورگر حفظ می‌شوند؛ زیرمسیر، مرز امنیتی مجزا برای localStorage نیست.
- مسیر proxy فعلی API فقط سرویس‌ها و عملیات مجاز همان پروژه را پوشش می‌دهد. صرف اضافه‌کردن دامنهٔ ir، تضمین رفع همهٔ محدودیت‌های شبکه نیست.
- برخی ماژول‌های آموزشی قدیمی intmed هنوز عکس‌ها یا کتابخانه‌هایی از دامنه‌های خارجی می‌خوانند. صفحهٔ شخصی، داشبورد AUS و پوستهٔ ورود intmed با فایل‌های محلی اجرا شدند؛ دسترس‌پذیری تمام منابع خارجی و همهٔ محتوای پس از ورود در این آزمون تأیید نشده است. این build لینک‌های آن‌ها را به پراکسی عمومی تبدیل نمی‌کند.

## مسیر AUS و دسترسی از ایران

نشانی انتخاب‌شده برای مخزن `4mirgr/immi_AUS`، آدرس `https://drgerami-md.ir/aus/` است. درخواست `/aus` در Pages به `/aus/` هدایت می‌شود تا فایل‌های نسبی و `data/*.json` از مسیر درست خوانده شوند. این مسیر redirect به GitHub یا iframe نیست؛ خود فایل‌های برنامه از hostname سایت ارائه می‌شوند. برای این بخش استاتیک، reverse proxy یا Supabase جدید لازم نیست.

ساخت ترکیبی باید اعتبارسنج رسمی خود AUS، یعنی `node scripts/validate-data.mjs`، و بررسی syntax فایل `app.js` را بگذراند. خطا مانع تولید خروجی می‌شود. هشدارهای غیرمسدودکنندهٔ upstream حذف یا مخفی نمی‌شوند و در گزارش build ثبت می‌شوند؛ نسخهٔ بررسی‌شده پنج هشدار قدیمی دربارهٔ دسته‌های کارها دارد که خود برنامه با شناسهٔ دسته نمایش می‌دهد. داده‌ها و منطق برنامه برای این انتقال بازنویسی نشده‌اند.

پسوند `.ir` به‌تنهایی به‌معنای میزبانی داخلی یا دسترسی تضمین‌شده در شبکهٔ ملی نیست. این چیدمان وابستگی بارگذاری AUS به GitHub و Google Fonts را حذف می‌کند، ولی در قطع اینترنت بین‌الملل ممکن است خود Cloudflare هم در دسترس نباشد. برای پوشش آن سناریو، همین خروجی استاتیک باید روی میزبان داخل ایران نیز ارائه شود و DNS/مسیریابی آن با مشخصات واقعی میزبان طراحی شود. این راه‌اندازی داخلی انجام نشده و هیچ میزبان یا IP حدسی تنظیم نشده است. وابستگی Supabase در intmed نیز همچنان جداگانه باقی است.

## تطبیق‌های خروجی، بدون تغییر مخازن پروژه‌ها

Build فایل‌های برنامه‌ها را بدون بازنویسی کپی می‌کند، به‌جز دو تطبیق مستند در خروجی: `intmed/sw.js` برای تشخیص مسیر محتوای زنده نسبت به scope جدید و نام‌گذاری مستقل کش؛ و `aus/styles.css` برای جایگزینی import فونت Google با فایل محلی Vazirmatn موجود در خروجی intmed. اولی مانع کهنه‌ماندن manifest/taxonomy و پاک‌کردن کش پروژهٔ دیگر می‌شود و دومی وابستگی بارگذاری داشبورد به Google Fonts را حذف می‌کند. اگر قرارداد این فایل‌ها در نسخهٔ بعد تغییر کند، build متوقف می‌شود تا adapter بازبینی شود.

در ریشه یک `sw.js` بازنشستگی قرار می‌گیرد تا service worker قدیمی intmed که قبلاً کل دامنه را کنترل می‌کرد، بتواند به‌روزرسانی و unregister شود. فقط کش‌های قدیمی `intmed-pwa-` پاک می‌شوند؛ localStorage، نشست، یادداشت‌ها و کش پروژهٔ جدید پاک نمی‌شوند. زمان دریافت به‌روزرسانی توسط دستگاه قدیمی به مرورگر و اتصال آن وابسته است؛ پذیرش انتقال روی دستگاه نصب‌شده باید جداگانه بررسی شود.

یک اسکریپت کوچک، recovery/inviteهای قدیمیِ دارای token در fragment ریشه را به `/intmed/` روی همان origin هدایت می‌کند. token در کد، لاگ یا درخواست خارجی قرار نمی‌گیرد. مسیر قدیمی `newsletter.html` نیز به نسخهٔ منتقل‌شده redirect می‌شود. لینک‌های عادی صفحهٔ اصلی منتقل نمی‌شوند.

یک `404.html` واقعی جلوی fallback تمام مسیرهای ناشناخته به صفحهٔ اصلی را می‌گیرد. `_redirects` اسلش انتهای مسیر پروژه‌ها را یکدست می‌کند. `_headers` برای config و service workerها کش قابل بازبینی تعیین می‌کند. این قواعد Pages باید پس از استقرار هم بررسی شوند؛ سرور سادهٔ Python شبیه‌ساز همهٔ رفتارهای Pages نیست.

## ساخت و آزمون محلی

برای دریافت خودکار نسخه‌های قفل‌شده:

```sh
python3 -m pip install -r requirements-cloudflare.txt
python3 scripts/build_cloudflare.py
python3 -m http.server 4173 --bind 0.0.0.0 --directory _site
```

برای استفاده از checkoutهای موجود و بررسی تطابق فایل‌ها:

```sh
python3 scripts/build_cloudflare.py --intmed-source /workspace/intMed-study-plan --aus-source /workspace/immi_AUS
python3 scripts/verify_cloudflare.py --intmed-source /workspace/intMed-study-plan --aus-source /workspace/immi_AUS
node scripts/cloudflare_sw_test.mjs
COMBINED_SITE=1 node scripts/browser-check.mjs
```

Build عمداً خروجی موجود را بازنویسی نمی‌کند. برای ساخت دوباره یک مسیر خالی با `--output` انتخاب کنید. با `GERAMI_SITE_DIR` مسیر خروجیِ آزمون Worker و با `GERAMI_PREVIEW_URL` آدرس سرور آزمون مرورگر را می‌توان تنظیم کرد. خروجی `_site` و sourceهای دریافت‌شده وارد commit نمی‌شوند.

نسخه‌های پروژه‌ها خودکار به آخرین commit شناور تغییر نمی‌کنند. پس از به‌روزرسانی مخزن اصلی، pin همان پروژه را بازبینی کنید، build و آزمون‌ها را اجرا کنید و سپس نسخهٔ ترکیبی را منتشر کنید. `build-info.json` در خروجی، نسخه‌های دقیق و adapterهای اعمال‌شده را ثبت می‌کند.

## قرارداد حفظ ساختار و قوانین intmed

- مرجع محتوا فقط `content/` و مرجع دسته‌بندی فقط `content/taxonomy.json` در مخزن اصلی می‌ماند. وب‌سایت شخصی دسته‌بندی یا نسخهٔ موازی از درس‌ها تولید نمی‌کند و `docs/content/` را دستی ویرایش نمی‌کند.
- ساخت ترکیبی قبل از ایجاد خروجی، `content_pipeline.py validate` و `content_pipeline.py check` همان نسخهٔ قفل‌شده را اجرا می‌کند. فایل تولیدشدهٔ کهنه یا محتوای ناسازگار، build را متوقف می‌کند؛ ابزار به‌صورت خودکار migrate/build نمی‌زند تا خطا را پنهان کند.
- آزمون‌های خود پروژه برای JavaScript، ورود و نشست، جداسازی و ادغام ذخیره‌ها، امتحان‌ها، ورود نام کاربری، مجوزها، PWA، gateway، پیکربندی runtime و preflight محلی نیز اجباری‌اند. شکست هر فرمان، انتشار این خروجی را مسدود می‌کند. فهرست کنترل‌های گذرانده در `build-info.json` ثبت می‌شود.
- checkout کثیف، حتی در قوانین یا منابع اصلی خارج از `docs/`، پذیرفته نمی‌شود. بعد از کنترل‌ها نیز تغییرنکردن checkout بررسی می‌شود.
- شناسه‌های مبحث، پاراگراف، سؤال، عکس و legacy anchorها بازنویسی نمی‌شوند. برنامهٔ حساب‌ها، تنظیم Supabase، نقش‌ها، دیتابیس و API از طریق این build جابه‌جا یا ویرایش نمی‌شوند. فقط adapterهای محدود و مستند بالا در خروجی وجود دارند.
- این کنترل‌ها جای CI کامل مخزن intmed، تأیید انسانی محتوای پزشکی یا پذیرش واقعی دستگاه/API را نمی‌گیرند. به‌روزرسانی pin باید پس از مرور AGENTS، قرارداد محتوا و تغییرات upstream انجام شود؛ برای انتشار نهایی، معیارهای همان پروژه باقی می‌مانند.

آزمون منفی سازنده، محتوای واقعاً نامعتبر، خروجی قدیمی و آزمون حسابِ شکست‌خورده را در checkout موقت آزمایشی بررسی می‌کند؛ هیچ مخزن اصلی یا حساب واقعی دست‌کاری نمی‌شود:

```sh
python3 -m unittest discover -s scripts -p 'test*.py'
```
