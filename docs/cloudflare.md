# Cloudflare: سایت شخصی، intmed و AUS واقعی

## منابع صحیح و مرزها

- سایت اصلی: `4mirgr/gerami-website`، شاخهٔ `main`.
- intmed: نسخهٔ قفل‌شدهٔ `4mirgr/intMed-study-plan`؛ محتوای معتبر آن در `/intmed/`.
- AUS واقعی: `4mirgr/immi-arash-amir`، رابط ورود در `/aus/` و backend همان Worker فعال `immi-arash-amir`.
- مخزن `immi_AUS` داشبورد قدیمی و بدون حساب بود و دیگر منبع پنل چندکاربره نیست. خروجی آن نباید به‌جای حساب‌های واقعی منتشر شود.

هیچ دیتابیس، کاربر، نقش، Google grant، کلید رمزگذاری، cron یا Worker موجودی توسط build ساخته یا تغییر داده نمی‌شود. Supabase مستقل AUS با Supabase intmed مخلوط نمی‌شود.

## تنظیم Pages

مخزن سایت شخصی را به Cloudflare Pages وصل کنید:

| تنظیم | مقدار |
|---|---|
| Branch | `main` |
| Framework | `None` |
| Build | `python3 -m pip install -r requirements-cloudflare.txt && python3 scripts/build_cloudflare.py` |
| Output | `_site` |
| Root directory | خالی |
| محیط build | Python 3.12+، Node 22+ و npm |

Build نسخه‌های دقیق `deploy/projects.json` را می‌گیرد. کنترل‌های اصلی intmed اجرا می‌شوند؛ frontend واقعی AUS در کپی موقت، با lockfile و پیشوند `/aus/` ساخته می‌شود. منابع اصلی و فایل‌های شخصی تغییر یا کپی نمی‌شوند. نصب npm و دریافت Git باید در محیط build مجاز باشند. برای دریافت مخزن خصوصی، دسترسی امن سرویس لازم است؛ رمز یا token در کد/چت نگذارید.

خروجی موجود بازنویسی نمی‌شود؛ برای تکرار محلی مسیر خالی با `--output` بدهید. Snapshot کامل شامل `wrangler.jsonc` واقعی intmed فقط برای آزمون‌های آن دریافت می‌شود؛ این فایل در ریشهٔ سایت عمومی منتشر نمی‌شود.

## مداخلهٔ لازم مالک: اتصال به Worker موجود

بعد از انتشار کد، در پروژهٔ Pages و بخش Settings → Bindings، یک **Service binding** بسازید:

- Variable name: **AUS_APP**
- Service/Worker: **immi-arash-amir**
- اتصال را برای محیط Production و، در صورت آزمون، Preview برقرار کنید و نسخهٔ جدیدی منتشر کنید.

Worker جدید، دیتابیس جدید یا clone از jobها نسازید. Worker `intmed-api-proxy` انتخاب این binding نیست. Secretها، GOOGLE_TOKEN_KEY، D1 و کلیدهای موجود را عوض نکنید.

بدون این binding، API جدید AUS عمداً 503 می‌دهد و هیچ داشبورد شخصی یا local-demo جایگزین آن نمی‌شود. جزئیات و محدودیت OAuth در [راهنمای درگاه](aus-gateway.md) است.

## مسیرهای جدید

| مسیر | رفتار |
|---|---|
| `/` | سایت شخصی |
| `/intmed/` | intmed؛ API قبلی آن حفظ می‌شود |
| `/aus/` | رابط ورود واقعی AUS |
| `/aus/api/*` | Pages Function به Worker موجود AUS |
| `/aus/supabase/auth/v1/*` | درگاه محدود احراز هویت همان Supabase اختصاصی AUS |
| `api.drgerami-md.ir` و مسیر API قبلی | دست‌نخورده، متعلق به intmed |

فقط دو پیشوند API مخصوص AUS به Functions می‌روند؛ فایل‌های استاتیک و API intmed با آن‌ها مخلوط نمی‌شوند. درخواست‌های خصوصی cache عمومی نمی‌شوند؛ Origin ورودی قبل از ارسال به Worker اعتبارسنجی می‌شود. هیچ مقصد دلخواهی از کاربر پذیرفته نمی‌شود.

اتصال‌های Google/LinkedIn موجود در همان backend باقی می‌مانند. شروع اتصال جدید و callbackهای وابسته به hostname تا تکمیل تنظیمات مجاز بسته می‌مانند؛ این محدودیت نباید با تغییر کلیدها یا مجوزهای عمومی دور زده شود.

## انتقال دامنه: آخرین مرحله

1. ابتدا `gerami-website.pages.dev`، صفحهٔ ورود AUS و خطای بسته‌بودن دسترسی بدون نشست را بررسی کنید. آزمون مصنوعی، سلامت حساب واقعی را ثابت نمی‌کند.
2. پس از binding، هر پزشک با حساب خودش ورود/خروج و دسترسی فقط به داده‌های خودش را بررسی کند. برای آزمون، هیچ پیام، ایمیل یا job واقعی خودکار اجرا نشود.
3. برای signup/recovery و اتصال جدید OAuth، callbackهای دقیق دامنهٔ نهایی باید در **پروژهٔ صحیح هر سرویس** افزوده و آزمایش شوند. تنظیمات قدیمی را قبل از پایان مهاجرت حذف نکنید.
4. سپس Custom domains پروژهٔ Pages را به `drgerami-md.ir` وصل کنید. مقصد فعلی GitHub Pages جایگزین می‌شود؛ از وضعیت فعلی DNS نسخهٔ قابل بازگشت داشته باشید.
5. رکوردهای ایمیل، Worker API intmed و nameserverهای nic.ir را دست نزنید. تغییر DNS به‌تنهایی پنل‌ها را ایجاد نمی‌کند.

API فعال، حساب‌ها و SQL تولید در این آماده‌سازی تغییر داده نشده‌اند. انتشار Git ممکن است build خودکار Pages را آغاز کند؛ binding و اتصال دامنه باید در پنل حساب مالک انجام شود.

## حفظ intmed و دسترسی شبکه

مرجع محتوای intmed همان canonical content و taxonomy است. validate/check و آزمون‌های اصلی آن اجباری می‌مانند. شناسه‌ها و فایل‌های محتوای تولیدشده بازنویسی نمی‌شوند. adapter محدود PWA، دامنهٔ کش را به `/intmed/` محدود می‌کند. Worker بازنشستگی ریشه و انتقال محدود لینک‌های قدیمی recovery برای مهاجرت وجود دارند؛ دادهٔ حساب و localStorage پاک نمی‌شوند.

این ساخت جای CI کامل پروژه‌ها، بازبینی انسانی پزشکی و آزمون واقعی دستگاه/شبکه را نمی‌گیرد. نسخه‌های upstream خودکار شناور نیستند و تغییر pin نیازمند مرور قراردادها و آزمون است.

پسوند .ir و Cloudflare تضمین دسترسی در قطع اینترنت بین‌الملل نیستند؛ میزبانی داخلی و وابستگی‌های خارجی باید جداگانه بررسی شوند. انتقال به دامنه، اتصال‌های چت را به OAuth وب‌سایت تبدیل نمی‌کند.
