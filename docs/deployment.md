# طرح استقرار و انتقال؛ هنوز اجرا نشده

دامنهٔ مقصد `https://drgerami-md.ir` است. این سند طرح انتقال است و هیچ تنظیم DNS، هاست، گواهی یا پروژهٔ موجودی را تغییر نمی‌دهد. انتشار محیط توسعه نیز به‌معنای استقرار سایت روی دامنه نیست.

**مسیر انتخاب‌شده پس از مشخص‌شدن میزبانی: [Cloudflare Pages](cloudflare.md).** دو پروژه بررسی شده‌اند: intmed دارای پوستهٔ استاتیک در `docs/` و API جداگانه است؛ AUS استاتیک است. برای میزبانی صفحات آن‌ها روی Cloudflare به Nginx یا VPS نیاز نیست. الگوی Nginx پایین این سند صرفاً گزینهٔ جایگزین برای مهاجرت آینده به VPS است.

## موارد باقی‌مانده پیش از انتقال واقعی

1. اتصال مخزن سایت شخصی به پروژهٔ Pages و بررسی build آزمایشی با تنظیمات راهنمای Cloudflare.
2. دسترسی مالک به تنظیمات فعلی دامنه، Worker/API و مقصدهای مجاز Supabase Auth.
3. زمان‌بندی تغییر اتصال دامنه با امکان بازگشت و آزمون دستگاهی که PWA قدیمی را نصب کرده است.
4. بررسی ورود، بازیابی و همگام‌سازی حساب واقعی پس از فعال‌سازی؛ هیچ حساب یا دادهٔ واقعی در آزمون محلی استفاده نشده است.

## نقشهٔ مطلوب

| مسیر | سرویس |
|---|---|
| `/` و `/pages/` و فایل‌های محلی سایت | وب‌سایت شخصی استاتیک |
| `/intmed/` | برنامهٔ واقعی intmed، مستقل |
| `/aus/` | برنامهٔ واقعی AUS، اگر قابل استقرار باشد |

DNS فقط نام میزبان را به مقصد وصل می‌کند؛ تفکیک زیرمسیرها در وب‌سرور یا سرویس میزبانی انجام می‌شود. قواعد پروژه‌ها باید قبل از fallback سایت اعمال شوند. نباید خطای 404 پروژه‌ها به صفحهٔ اصلی سایت تبدیل شود. حالت دارای اسلش و بدون اسلش را یکدست کنید و پارامترهای query را نگه دارید.

## کنترل سازگاری زیرمسیر

- آیا برنامه مسیر پایهٔ قابل تنظیم دارد؟ فایل‌های `/assets` و مسیرهای مطلق `/api`، router، manifest، service worker و deep linkها را بررسی کنید.
- قرارداد عبور prefix به upstream را براساس برنامه انتخاب کنید؛ حذف یا حفظ `/intmed/` به‌صورت حدسی می‌تواند صفحهٔ اصلی را سالم ولی صفحات داخلی را خراب کند.
- redirectهای ورود، callback، WebSocket و URL عمومی برنامه باید با مسیر جدید تطبیق داشته باشند.
- نام و Path کوکی‌ها، کلیدهای localStorage و دامنهٔ service worker پروژه‌ها را بررسی کنید. زیرمسیرها مرز امنیتی مستقل نیستند؛ اگر جداسازی لازم است از زیردامنه و طراحی احراز هویت مناسب استفاده کنید.
- اگر برنامه بدون تغییر کد با زیرمسیر سازگار نیست، تنظیمات رسمی base path یا زیردامنه‌های `intmed.drgerami-md.ir` و `aus.drgerami-md.ir` را بررسی کنید. «بدون تغییر ساختار» به‌معنای تضمین «بدون تغییر تنظیمات» نیست.

## ترتیب انتقال

1. پشتیبان از برنامهٔ موجود، داده‌ها و تنظیمات؛ حفظ سرویس فعلی تا موفقیت بررسی staging.
2. استقرار آزمایشی هر برنامه در مسیر هدف، بدون تغییر ساختار داخلی یا کپی محتوای خصوصی در مخزن سایت.
3. بررسی لینک‌های داخلی و deep link، assetها، ورود/خروج، API و مجوزها؛ سایت اصلی و هر دو پروژه باید مستقل تست شوند.
4. تهیهٔ نگاشت URLهای قدیمی به مقصد دقیق در `/intmed/`. برای هر مورد جابه‌جاشده redirect دائمی مناسب تنظیم شود. نشانی ریشهٔ قدیمی نمی‌تواند هم‌زمان هم صفحهٔ اصلی جدید باشد و هم redirect به intmed؛ این تعارض باید آگاهانه حل شود.
5. هنگام استقرار عمومی، HTTPS، canonicalها، دسترسی دامنه و نشانی واقعی پروفایل‌ها را بررسی کنید. canonicalهای فعلی برای ساختار `/pages/*.html` هستند؛ اگر URLها تغییر کردند آن‌ها را اصلاح کنید. برای همین نسخهٔ دوزبانهٔ مشترک، URL انگلیسی جداگانه ادعا نشده است.
6. تنها پس از موفقیت مراحل بالا، `intmed` و `aus` را در `js/links.js` فعال کنید. راه برگشت به تنظیمات قبلی را نگه دارید.

## دسترسی از دامنهٔ ir و نقش reverse proxy

دو دکمهٔ صفحهٔ اصلی و صفحهٔ پروژه‌ها مستقیماً به `https://drgerami-md.ir/intmed/` و `https://drgerami-md.ir/aus/` اشاره می‌کنند؛ این دکمه‌ها بدون JavaScript هم دیده می‌شوند. تا اتصال واقعی سرویس‌ها، پیام وضعیت به‌وضوح اعلام می‌کند که اتصال تکمیل نشده است. کارت‌های توضیحی تا زمان تأیید استقرار همچنان به معرفی پروژه می‌روند. تنظیم لینک کارت‌ها، لینک ورود را به دامنهٔ خارجی تبدیل نمی‌کند.

اگر پروژه‌ها جداگانه اجرا می‌شوند، Nginx یا پراکسی معکوسِ معادل روی ورودی دامنه لازم است تا درخواست‌ها را در سمت سرور به برنامهٔ مناسب برساند. اگر فایل‌های هر دو پروژه استاتیک و سازگار با زیرمسیر باشند، میزبانی مستقیم پوشه‌ها کافی است و پراکسی برنامه لازم نیست. redirect به سایت خارجی یا iframe باعث نمی‌شود درخواست‌های آن سایت از سرور ir عبور کنند.

```text
مرورگر کاربر
    │ HTTPS: drgerami-md.ir
    ▼
وب‌سرور / reverse proxy
    ├── /          ← فایل‌های سایت شخصی
    ├── /intmed/   ← برنامهٔ مستقل intmed
    └── /aus/      ← برنامهٔ مستقل AUS
```

با میزبانی خود برنامه‌ها و فایل‌های لازم روی سرور قابل دسترس، وابستگی مرورگر به میزبان خارجی کاهش می‌یابد. اگر API، فونت، تصویر، صفحهٔ ورود یا درخواست JavaScript همچنان مستقیماً به دامنهٔ خارجی برود، همان محدودیت می‌تواند باقی بماند. تمام مسیرهای موردنیاز، redirectها و هدرهای تولیدشده باید با دامنهٔ عمومی جدید سازگار شوند؛ تغییر لینک به‌تنهایی این کار را انجام نمی‌دهد.

دامنهٔ ir به‌تنهایی ضمانت عبور از فیلترینگ، قطعی یا محدودیت شبکه نیست. محل میزبانی، مسیر ارتباط کاربر تا سرور و دسترسی خود سرور به upstreamها تعیین‌کننده‌اند. اگر سرور داخل ایران باشد ولی به سرویس خارجی قطع‌شده نیاز داشته باشد، reverse proxy به‌تنهایی آن وابستگی را برطرف نمی‌کند. میزبانی مستقل سرویس‌های لازم، در صورت امکان، پایدارتر است.

## الگوی Nginx

[الگوی بررسی‌پذیر](../deploy/nginx.conf.example) برای دو برنامهٔ مستقل روی همان سرور تهیه شده است. این فایل فعال نشده و پورت‌ها و مسیر گواهی آن عمداً جای‌نگهدار هستند. برنامه‌ها باید رسماً با پیشوند مسیرشان سازگار باشند. این الگو با نسخهٔ نصب‌شدهٔ Nginx روی سرور مقصد باید بررسی شود؛ در محیط فعلی Nginx نصب نیست.

1. `__INTMED_PORT__` و `__AUS_PORT__` را با پورت‌های واقعی برنامه‌های loopback جایگزین کنید.
2. مسیرهای `__FULLCHAIN_PEM_PATH__` و `__PRIVATE_KEY_PEM_PATH__` را با گواهی معتبر دامنه تنظیم کنید. کلید خصوصی را در مخزن نگذارید.
3. فقط `index.html`، `pages/`، `css/`، `js/` و `favicon.svg` را در ریشهٔ عمومی مشخص‌شده کپی کنید؛ metadata گیت و فایل‌های خصوصی را منتشر نکنید.
4. این الگو باید در context نوع `http` بارگذاری شود. با پیکربندی فعلی سرور ادغام و تداخل server_name بررسی شود؛ روی سرویس موجود جایگزینی کور انجام ندهید.
5. ابتدا `nginx -t` و آزمون‌های staging را اجرا کنید. فقط پس از موفقیت و با دسترسی مجاز سرور، reload انجام شود. این کارها در این گفتگو انجام نشده‌اند.

الگو prefix مسیر را حفظ می‌کند. صرف افزودن اسلش به `proxy_pass` بدون بررسی برنامه ممکن است assetها و مسیرها را خراب کند. اگر upstream از طریق HTTPS روی میزبان دیگری باشد، مقصد واقعی، SNI و اعتبارسنجی گواهی آن باید صریحاً پیکربندی شوند؛ TLS verification را غیرفعال نکنید. این الگو پراکسی باز عمومی نیست و نباید مقصد دلخواه را از ورودی کاربر بپذیرد.

تا قبل از دریافت برنامه‌ها و مشخصات هاست، اجرای واقعی و سازگاری آن‌ها با این مسیرها تأیید نشده است.
